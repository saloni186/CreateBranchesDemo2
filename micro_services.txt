Microservices :
1)what are microservices and why they are used
Microservice is an architectural style where an application is divided into small, independent services. Each service handles one specific business capability and can be developed, deployed, and scaled independently.Why they are used:

Scalability: Each service can be scaled separately.

Flexibility: Different teams can work on different services using different technologies.

Fault Isolation: If one service fails, it doesn’t crash the entire system.

Faster Deployment: Small services are easier to test and deploy.

what are the chalenges of microservices acrchitechture

what are the chalenges :-

Complexity: Managing many small services is more complicated than a single application.

Data Management: Each service may have its own database, making transactions and consistency harder.

Communication: Services need to talk to each other over the network, which can cause latency or failures.

Monitoring & Debugging: Tracing issues across services is harder than in a monolithic app.

Security: Each service needs proper authentication and authorization, increasing security concerns.

In short: microservices give flexibility and scalability but add operational and architectural complexity.

 what is curcite breaker in microservices
Ansc :-Problem it solves

In a microservices system, Service A might call Service B.

If Service B is down or slow, Service A keeps waiting or retrying.

This can slow down or even crash the entire system.

Circuit Breaker prevents this problem by stopping repeated failing calls.

2. How it works (3 states)

Closed ✅

Everything is normal. Requests go to the service as usual.

Open ✋

Too many failures happened. The circuit “opens,” so requests don’t go to the failing service. Instead, fallback logic is used.

Half-Open 🔄

After some time, the system tests the service with a few requests.

If successful → circuit closes.

If failures continue → circuit stays open.

what happened if one service has down so entire system is failed what happen?
Ans :-What happens if one service goes down?

In a microservice system:

Client → API Gateway → Service A → Service B → Service C


If Service B goes down:

Any request that depends on B fails.

The client may see an error or timeout.

So, the system doesn’t fully fail, but the part of the system depending on that service is unavailable.

2️⃣ How microservices handle this
🔹 1. Circuit Breaker

Detects failure in a service.

Stops calling it temporarily to avoid cascading failures.

Examples: Resilience4j, Hystrix.

Service A calls B → fails repeatedly → Circuit Breaker opens → requests fail fast instead of waiting

🔹 2. Retry

Retry a failed request a few times before giving up.

Avoid overloading the failing service.

🔹 3. Fallback

Provide default behavior when a service is down.

Example:

if CompanyService is down → return "Company info not available"


User doesn’t see a full crash.

🔹 4. Load Balancing & Multiple Instances

Run multiple instances of each service.

If one instance is down → requests go to healthy instances.

Done via Eureka, Kubernetes, or Consul.

🔹 5. Queue / Asynchronous Messaging

Use Kafka, RabbitMQ to decouple services.

If a service is down, messages stay in the queue → processed later.

Prevents immediate failures.

3️⃣ Key idea

In microservices, one service down doesn’t bring down the entire system, if the system is designed with resilience patterns: circuit breakers, retries, fallbacks, load balancing, and async messaging.

if service a calls service b multimul time so hao can you improves the performance here?
Ans :-Ah! You’re asking about optimizing repeated calls between microservices — this is a common performance bottleneck. Let’s break it down clearly.

Problem
Service A → Service B → Service C


Service A calls Service B multiple times (maybe in a loop).

Each call → network latency + serialization/deserialization → slows down the system.

We need ways to reduce network calls and improve performance.

1️⃣ Caching

Cache responses from Service B in Service A (or in a distributed cache).

Reduces repeated network calls.

Example:

@Cacheable(value = "companyCache", key = "#id")
public Company getCompany(Long id) {
    return companyClient.getCompany(id);
}


Tools: Spring Cache, Redis, Caffeine

✅ Pros: Fast, reduces load on Service B
❌ Cons: Data may be stale → handle cache invalidation

2️⃣ Bulk / Batch Calls

Instead of calling Service B many times individually, call once with a batch of IDs.

Before:

for(Long id: ids) {
   companyClient.getCompany(id);
}


After:

companyClient.getCompanies(ids); // returns list at once


✅ Pros: Less network overhead
✅ Often simplest and most effective

3️⃣ Asynchronous Calls

Use async requests instead of blocking calls.

Service A can call B in parallel → wait for all results together.

CompletableFuture<Company> future = CompletableFuture.supplyAsync(() -> companyClient.getCompany(id));


✅ Pros: Improves throughput
❌ Cons: Complexity increases

4️⃣ Combine Cache + Async + Batch

For frequent requests, cache + batch call is extremely efficient.

Example flow:

Check cache → found → return

Not found → batch call → update cache → return

5️⃣ Use Event-Driven / Messaging

If Service B updates data frequently, instead of pulling repeatedly, push updates to Service A via Kafka/RabbitMQ.

Service A subscribes → always has latest data locally.

✅ Pros: Reduces synchronous calls
❌ Cons: Eventual consistency

6️⃣ Use HTTP/2 or gRPC

HTTP/1.1: Each call = new TCP connection

HTTP/2 / gRPC: Multiplex multiple calls over same connection → lower latency

✅ Summary (for interview answer)

To improve performance when one service calls another multiple times, use caching, batch calls, asynchronous requests, event-driven updates, or high-performance protocols like gRPC.

  metrics:
  - type: Resource
    resource:
      name: cpu

        type: Utilization
        averageUtilization: 70

🔹 2. Load Balancing

Use API Gateway / Ingress / Service Mesh

Distribute traffic across multiple instances.

🔹 3. Caching Layer

Cache frequently accessed data → reduces load on services & DB.

🔹 4. Queue / Asynchronous Processing

Move non-critical tasks to queues → decouple services.

Example: send emails, notifications, report generation.

Tools: Kafka, RabbitMQ, SQS

🔹 5. Database Scaling

Partitioning / sharding for writes if needed

Protect services from overload

Stateless services → easy to scale

Idempotent operations → retries are safe

Asynchronous communication → prevents blocking

✅ Summary

To handle sudden 10x traffic:

Scale services horizontally (Kubernetes / cloud auto-scaling)

Use load balancer / API Gateway

Add caching for hot data

Queue non-critical tasks (Kafka / RabbitMQ)

Scale databases with replicas / sharding

Apply rate limiting and backpressure

whta are you think use microservices itself why we use monolithic if there is many advantades of microservices ?
Ans :-Advantages of Microservices

Yes, microservices are awesome for:

Scalability: Scale only the service you need.

Independent deployment: Deploy without touching the entire system.

Fault isolation: One service down ≠ entire system down.

Rewriting everything in microservices may not be worth the cost.

Monolith	Microservices

Microservices are not always better. They shine for large, complex, scalable systems, but add operational and architectural overhead.
Monoliths are simpler, cheaper, and faster for small apps or startups.

what happens when two staters provides same bean ?
Ans :-You have two starters on the classpath: starter-A and starter-B.

Both define a bean with the same type and name:

@Bean
public MyService myService() {
    return new MyService();
}

What Spring Boot does:
1️⃣ By default: ApplicationContext fails to start

Spring sees two beans of the same type AND same name.

It throws:

org.springframework.context.annotation.ConflictingBeanDefinitionException: 
Bean definition with name 'myService' defined in ...

2️⃣ How to avoid conflicts
🔹 Option 1: Use @ConditionalOnMissingBean

Most Spring Boot starters use this:

@Bean
@ConditionalOnMissingBean
public MyService myService() {
    return new MyService();
}


Meaning: only create this bean if no other bean of this type exists.

Now your starter coexists safely with other starters.

🔹 Option 2: Qualifiers / Custom Bean Names

Give beans different names:

@Bean("starterAMyService")
public MyService myService() {
    return new MyService();
}


Or use @Qualifier when injecting:

@Autowired
@Qualifier("starterAMyService")
private MyService service;

🔹 Option 3: Primary Bean

Let one bean be primary:

@Bean
@Primary
public MyService myService() {
    return new MyService();
}


If multiple beans exist, Spring injects the primary bean by default.

✅ TL;DR

If two starters provide the same bean, Spring will fail to start unless you handle it with:

@ConditionalOnMissingBean ✅ (preferred for starters)

@Primary

Bean names + @Qualifier
